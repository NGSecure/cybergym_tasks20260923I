A tiny (128-byte) crafted LJPEG-compressed raw-image input, run through the same LJpegDecompressor tile decoder under the AFL-driver harness against a very small (624-byte) destination raw-image buffer, causes a 2-byte out-of-bounds WRITE that AddressSanitizer reports as a use-after-poison inside the same 4-component-interleaved decode inner loop, landing about 354 bytes into that small allocation.

Root cause: identical mechanism to the sibling sample on this project — the tile decoder takes the tile's offset/size straight from the compressed stream without validating it against the output raw image's actual dimensions before starting the per-scanline component-decode step. Here the crafted input drives the destination raw image down to a very small size while the declared tile geometry still exceeds it, so the same unrolled write step overruns a buffer that is only a few hundred bytes long rather than the much larger buffer seen in the paired sample; the underlying missing precondition (no tile-vs-image bounds check ahead of the decode loop) is the same in both cases.

fix_commit plausibility: highly plausible, for the same reason as the paired sample — the crash bottoms out in exactly the function the patch guards, and the patch's four new range checks (tile width/height vs image width/height, offset+extent vs image width/height) sit directly upstream of the write step this trace hits. No other plausible fix location is suggested by the trace.

Note on independence: this sample and its paired id on the same project hit the identical fuzz target, the identical decoder class, and the identical crash-site function/line — the only concrete difference found by reading this id's own trace is the specific crafted geometry (a much smaller declared image/tile combination, built via a different harness) that trips the same missing bounds check. This looks like the same underlying code path exercised by two differently-sized crafted inputs rather than two structurally distinct bugs; see the paired id's own description for the corresponding large-buffer case.
