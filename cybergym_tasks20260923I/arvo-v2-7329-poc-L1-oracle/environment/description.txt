A bug in ImageMagick's HEIC/HEIF item-properties-container parser (ASan heap-buffer-overflow READ, multi-byte) occurs while pinging a crafted HEIC file. The generic property-container walker allocates a destination buffer for each property's payload, deliberately sized a few bytes larger than the file-declared payload length so that a later specialized per-property-type parser has a little headroom to write derived fields past the raw declared data. To fill that destination buffer, the walker copies bytes out of a source region that only ever holds the file-declared payload itself — but the copy length used is the padded destination size rather than the real declared payload size, so the copy reads a handful of bytes past the end of the (correctly, tightly sized) source region.

The fix corrects the copy to only pull the actual declared payload length out of the source, and separately zero-initializes the destination buffer's full padded extent up front, so the extra headroom bytes end up as a defined value (zero) rather than either uninitialized memory or bytes read out-of-bounds from the source.

fix_commit plausibility: highly plausible: the diff sits in exactly the property-container walker on the crash's own call chain, correcting a copy-length mismatch between a padded destination allocation and its unpadded source, which precisely matches a read that lands just past a source region whose size exactly matches the file-declared payload.
