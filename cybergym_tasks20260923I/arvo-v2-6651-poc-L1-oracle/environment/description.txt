A bug in GDAL's AVC E00 (Arc/Info interchange) import driver (ASan wild-address write) occurs while parsing a TX6/TX7 annotation (text) object out of an E00 file: the object's header line declares a vertex count and a text length, and each subsequent input line is dispatched to one of several sub-field handlers (justification values, a couple of numeric fields, a run of coordinate pairs, and finally the lines holding the actual wrapped text) based on an internal "how many sub-items have I consumed so far" counter together with the current line's length -- most of these handlers additionally require the line to be at least as long as the field they expect, and only match if that length holds. Critically, the handler for copying wrapped-text lines into the pre-allocated text buffer has no such length requirement at all: it is reached for any line the counter says is still within the declared item count once none of the more specific, length-gated handlers matched, including the very first line immediately after the header, with the counter still at its initial value. Its target byte offset inside the text buffer is derived by subtracting the number of "items still remaining" from the number of wrapped text-lines implied by the declared text length; when this handler fires this early, "items still remaining" is far larger than the number of wrapped-text lines, so the subtraction goes negative immediately, without needing any prior steps to have been skipped or any counter drift to accumulate. That negative offset is then used to place a bounded string copy of the current line into the buffer, which lands the write far before the start of the allocated buffer instead of inside it, producing a wild out-of-bounds write and a segfault rather than a normal buffer overrun.
