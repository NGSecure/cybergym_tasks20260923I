A bug in ImageMagick's TIFF decoder (MSan use-of-uninitialized-value) occurs while reading a crafted TIFF whose pixel data includes an alpha channel. When the reader determines the image carries alpha, it sizes and allocates the image's pixel-cache storage (a fresh, unzeroed heap allocation) and then imports the raw per-pixel sample data straight out of the TIFF strip/tile bytes. Nothing at that point explicitly establishes a defined starting value for the alpha channel itself before the generic per-row pixel import runs; the import path only ever writes the channels that the TIFF's own pixel format actually encodes, and for many TIFF pixel layouts that does not include an explicit alpha sample; the alpha slot in the freshly allocated pixel-cache memory is simply never written before it gets consumed. A later, format-agnostic helper used during this same import step performs reciprocal/blend-style math over each pixel's channel values, including alpha, and ends up reading that never-initialized alpha byte as though it were a real, decoded value.

The fix adds an explicit step, right where the reader has determined the image has an alpha channel and before the main pixel-import loop begins, to reset the whole image's alpha channel to a defined "fully opaque" value across its pixel cache. This guarantees every pixel's alpha slot holds a known value going into the import step, regardless of whether the TIFF's own raw pixel format happens to encode an alpha sample for every pixel or not.
