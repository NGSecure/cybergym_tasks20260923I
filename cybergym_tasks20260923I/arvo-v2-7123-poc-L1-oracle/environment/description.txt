A crafted, malformed TIFF image, run through the same ImageMagick PTIFF fuzz harness (Magick::Image::read into ImageMagick's own TIFF reader, which then calls into the vendored libtiff library's RGBA-strip conversion path), causes a 4-byte out-of-bounds READ that AddressSanitizer reports landing exactly at the right edge of a several-thousand-byte heap allocation — the read happens inside the same libtiff strip-to-RGBA conversion routine that fills the output pixel buffer strip by strip, but not during that per-strip fill itself. It happens in a short finishing pass the routine runs afterward, once every strip has already been decoded and unpacked into the buffer: for TIFF images whose orientation tag records a horizontal flip, the routine walks back over each completed output row and swaps it end-to-end in place. That row-reversal pass is what reads past the buffer's real end.

Root cause: this is the same underlying bug as a sibling sample built from this project. ImageMagick's own TIFF reader allocates the working pixel buffer that libtiff will fill via a "take the largest of a few candidate size estimates" comparison — one estimate derived from the strip's raw scanline size, one derived from the image's width and bit depth, and one derived from the strip's row count. One of these candidate estimates omits a factor that should scale together with the image's declared width; for TIFF inputs whose width/strip geometry make that particular (width-blind) estimate dominate the comparison, the resulting buffer ends up materially smaller than the routine believes it is when it later walks the buffer using the image's declared width and height. The per-strip decode-and-unpack calls that run first happen to stay within the (undersized) buffer for this crafted input and complete without incident; it is only the trailing row-reversal pass — walking outward from both ends of each row, all the way to the declared width — that steps one 4-byte element past the real end of the allocation on the buffer's final row.

Note on independence: this sample shares its fix commit and root cause with a sibling id on this same project, but the two are reproduced by differently-crafted images that drive the same undersized buffer down different points of the same enclosing libtiff routine. This sample's crafted geometry survives the routine's whole per-strip decode-and-unpack pass over the (undersized) buffer without incident, and is only caught reading out-of-bounds afterward, during that routine's trailing row-reversal housekeeping step; the sibling's crafted geometry instead overruns earlier and by a much wider margin, during the per-strip pass itself, in a bit-depth-specific unpacking step reached for a different (1-bit bilevel) pixel format. Both are two independently-reproducible crafted inputs against one shared allocation bug rather than two structurally distinct vulnerabilities — treat them as needing one fix, not two.

fix_commit plausibility: highly plausible. Two independent signals point to this commit: OSS-Fuzz's own ClusterFuzz automated fix-range bisection closed this issue against exactly this commit (independently of the sibling sample's own bisection landing on the same commit), and the change the commit makes is precisely the allocation-size computation that sizes the buffer this crash trace's own allocation frame — visible earlier in the same call stack, inside ImageMagick's TIFF-reading module — creates, and which the routine's trailing row-reversal pass then reads one element past. The fix's recorded touched file also correctly names ImageMagick's own TIFF-reading module rather than the vendored libtiff library where the crash itself lives, consistent with a caller-side sizing bug rather than a defect in libtiff's own row-reversal logic.
