A bug in ImageMagick's Windows ICO/icon reader (MSan use-of-uninitialized-value, surfacing deep inside the bundled zlib/libpng checksum code) occurs when an icon directory entry declares that its image data is actually an embedded PNG. The reader allocates a buffer sized to the entry's declared total length, writes a small fixed header into the first bytes itself, and then issues a single read for the remaining declared length directly into the rest of that buffer. It only checks that this read returned *some* positive number of bytes before treating the whole buffer as a complete, valid embedded PNG stream and handing it off to the PNG decoder — it never confirms the read actually delivered the full number of bytes the entry claimed. If the underlying blob is truncated so the read comes up short, the tail of the buffer past what was actually read is left as raw, never-written heap memory, yet is still passed to the PNG decoder as if it held real trailing chunk bytes. When the decoder later computes a checksum over one of those unknown/ancillary chunks, it walks into that unwritten tail.

The fix tightens the check from "did we read anything" to "did we read exactly the declared number of bytes," so a short/truncated read now causes the reader to skip treating the entry as an embedded PNG at all, instead of proceeding with a buffer that's only partially populated.

fix_commit plausibility: highly plausible: the diff changes exactly the read-length validation immediately after the read call in the icon-decoding routine that sits at the top of the crash's allocation-origin stack — from a loose "non-empty" check to an exact-length check — precisely closing the gap that let a short read still be treated as a fully valid, fully-populated buffer.
