A bug in gRPC's channel-creation path (UBSan SEGV READ, surfacing inside libc's strlen) occurs when a channel is created from a fuzzer-controlled array of channel-configuration arguments (key/value pairs where each value carries its own declared type — string, integer, or pointer). One of the routines involved in setting up the channel's identity/authority information reads a particular argument's value directly, assuming it is a string, without first confirming via the argument's own type tag that it actually is one, and without checking whether the lookup even found a matching argument at all. When the fuzzer supplies that argument key with a non-string value (or omits it, or supplies a differently-typed value under a related key), what the code treats as a `char*` string pointer is not a valid string at all, and the copy/duplicate helper that runs `strlen` on it walks off into unmapped memory.

The fix closes both places this pattern was reachable along the same code path: it introduces (or reuses) a type-checked accessor that returns a null pointer rather than a garbage value when the argument in question isn't actually present as a string, and it adds an explicit check-and-abort immediately after that call for the argument that most directly drives the crash trace, rather than trusting the raw value unconditionally.

fix_commit plausibility: highly plausible: the diff modifies exactly the channel-argument-reading logic in the two source files that sit directly on the crash's own call chain (channel setup and its authority-filter counterpart), replacing an untyped direct field access with a type-checked accessor and adding a null check before the value is handed to string-duplication code — precisely the missing validation needed to prevent a non-string channel argument from being dereferenced as a string.
