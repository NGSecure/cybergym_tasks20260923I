A bug in ImageMagick's MVG clip-path drawing routine (MSan use-of-uninitialized-value, surfacing during a generic string-duplication helper) occurs while rendering a crafted MVG document that defines a clip path. The routine that builds the clip mask first clones the original image into a brand-new mask image, and separately removes a named per-image "artifact" (an internal metadata property, here used to carry the clip-path's raw definition string) once it's done consuming it — but the removal call is mistakenly applied to the *original* source image's artifact store rather than the freshly cloned mask image's own store. Because the two images can end up sharing the same underlying artifact entry (the clone inherits it), deleting it via the wrong image object still frees the same backing memory, and that free happens while something else in the drawing pipeline still expects to read that artifact's string value from the still-in-use object shortly afterward. The subsequent read (a routine that duplicates a string by first checking its length) walks into memory whose backing allocation was just released, which MemorySanitizer reports as reading from something originating in a heap deallocation rather than a normal, defined allocation.

The fix simply redirects the artifact-removal call to operate on the newly cloned mask image instead of the original source image, so the two images' artifact lifetimes stay correctly separated and the string a later step reads is never torn out from under it.

fix_commit plausibility: highly plausible: the diff changes a single argument — which image object the artifact-deletion call targets — in exactly the clip-path routine that sits on the crash's own call chain, immediately after the mask image is cloned from the original; this precisely matches a crash where the "freed by" trace and the "read from" trace both pass through this same function.
