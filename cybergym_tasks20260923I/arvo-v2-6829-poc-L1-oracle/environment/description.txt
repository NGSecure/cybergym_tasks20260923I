A crafted LJPEG-compressed raw-image bitstream, run through the LJpegDecompressor tile decoder (libFuzzer harness, ~648KiB destination raw-image buffer), causes a 2-byte out-of-bounds WRITE that AddressSanitizer reports as a use-after-poison inside the 4-component-interleaved decode inner loop, ~75KB into the destination allocation.

Root cause: before dispatching to the per-scanline component-decode routine, the LJPEG tile decoder accepts the tile's offset and size (offsetX/offsetY/width/height) straight from the compressed stream and never checks them against the actual output raw image's dimensions. When the declared tile extent is inconsistent with the image the destination buffer was sized for, the unrolled 4-component write step keeps writing samples past the region that was actually allocated/initialized for that image, landing in still-poisoned (never-written) memory beyond the legitimate data — i.e. a missing tile-vs-image bounds check ahead of the decode loop, not a bug in the loop's arithmetic itself.

fix_commit plausibility: highly plausible. The one function the crash trace bottoms out in is exactly the function the patch instruments — the patch inserts four new range checks (tile width/height vs image width/height, and offset+extent vs image width/height) immediately before the point where geometry is accepted and the tile decode begins; that is precisely the missing precondition this crash exercises (an over-large/mis-offset tile decoded against an undersized destination buffer). No other plausible fix location is suggested by the trace.
