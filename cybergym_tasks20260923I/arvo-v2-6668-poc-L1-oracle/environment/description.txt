In GDAL's Arc/Info Binary Coverage (AVC) binary reader (ASan build), the per-record vertex count is read straight from the input file as a signed integer and stored into the reader's persistent per-arc state unconditionally, without checking that it is non-negative — even on a record where the count is small enough that no buffer resize is needed. Because the vertex buffer is only reallocated when the new count exceeds the *previously stored* count, a crafted record that supplies a negative count first drives that stored "high-water mark" negative without touching the buffer at all; a later, otherwise unremarkable record whose count is merely small (e.g. zero) then satisfies that stale negative threshold and triggers a resize down to a near-zero byte count. On this build that resize call frees the existing buffer and returns null, and the caller's allocation-failure path returns immediately without recognizing the buffer is already gone, so the struct's pointer to it is left dangling rather than cleared. When the layer is subsequently reset/reused and the reader tears down its per-arc state, it frees that same pointer again, aborting with a heap double-free.
