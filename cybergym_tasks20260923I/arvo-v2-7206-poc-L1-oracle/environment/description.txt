A bug in librawspeed's Sony ARW raw-image decoder (MSan use-of-uninitialized-value) occurs while decrypting and re-parsing the camera's white-balance metadata sub-IFD. TIFF-style offsets inside that metadata are absolute, counted from the very start of the original encrypted region, not from wherever the decrypted copy happens to begin — so when the decoder allocates a fresh buffer to hold the decrypted bytes and copies the decrypted portion starting partway into it (leaving room in front for that absolute-offset arithmetic to keep working), the leading portion of the new buffer, before where the real decrypted bytes begin, is never written to at all; it is raw, freshly-allocated heap memory.

The decoder then hands the whole buffer — leading gap included — to the generic recursive TIFF-IFD parser, along with the starting offset into it where the real data begins. Nothing at that point stops the IFD-entry-walking logic from treating some computed offset that lands inside the unwritten leading gap as if it referenced valid, already-decrypted metadata, and reading it as such. Because the parser has no independent way to know that region was never populated, it happily reads and interprets that garbage the same way it would real data, which is what MemorySanitizer flags.

The fix keeps the same buffer layout (decrypted data still starts partway into the allocation, for the same absolute-offset reason) but explicitly registers that leading gap as its own known, reserved region in the same overlap-tracking data structure the IFD-entry walker already consults to validate offsets against known buffer extents. With the gap recorded as an off-limits region rather than being invisible to that bookkeeping, any subsequent reference that lands inside it is now recognized as invalid by the existing validity machinery instead of being silently treated as ordinary metadata and read from.

fix_commit plausibility: highly plausible: the diff sits directly in the white-balance-metadata routine on the crash's own allocation-origin call stack, and the "uninitialized value was created by a heap allocation" trace's malloc call matches precisely the buffer this diff resizes and augments — the fix's explicit comment about the decrypted root IFD not being allowed to point into the preceding padding region names the exact failure mode the trace demonstrates.
