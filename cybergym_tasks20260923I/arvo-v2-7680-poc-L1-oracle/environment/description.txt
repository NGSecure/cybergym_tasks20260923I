ImageMagick's ICO/CUR reader extracts an embedded PNG sub-image from inside an icon directory entry and hands it to libpng for decoding. To do this it builds a synthetic PNG source buffer of its own: it allocates one heap block sized to hold a fixed 16-byte header region (which it fills in itself, deriving values such as width/height/planes/bits-per-pixel from the icon directory entry) plus the PNG payload that follows in the input stream, where the payload region's size is taken directly from the icon directory entry's declared length field. The read that fills the payload portion, however, is told to read 16 bytes fewer than that declared length, even though the full declared length (plus the 16-byte header) is later passed to the PNG decoder as the total buffer size. The result is that the trailing 16 bytes of the allocated block are never written by anything — they hold whatever the allocator handed back — yet the decoder is told the buffer is fully sized and payload-complete, so it walks all the way to the end of it while parsing.

libpng consumes the buffer as an ordinary PNG stream: it reads a chunk's declared length and type, verifies the chunk's CRC by hashing the type+data bytes it just read, and — for chunk types it does not itself recognize — additionally copies the raw chunk bytes into a scratch buffer for later reuse instead of discarding them. Depending on how the payload bytes happen to be laid out, the trailing unwritten span can fall inside a chunk's length/CRC-relevant span read at the very start of parsing, or only get touched once an unrecognized ancillary chunk near the end of the stream is looked at and its data range is copied and hashed. Either way, arithmetic and comparisons that libpng performs while validating the chunk are done over bytes that were never written by the ICO reader, which a memory-sanitizer build flags as use of an uninitialized value — despite there being no out-of-bounds access, since the block itself is large enough and the extra 16 bytes are legitimately allocated, just never populated before being read.

Fixing this requires making the payload read consume the full declared payload length (matching what is actually allocated and later handed to the decoder) instead of stopping 16 bytes short of it, so every byte of the buffer that the PNG decoder is told exists has actually been written before decoding begins.
