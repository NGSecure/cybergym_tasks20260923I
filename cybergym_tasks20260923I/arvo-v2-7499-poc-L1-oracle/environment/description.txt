A bug in ImageMagick's PNG reader (MSan use-of-uninitialized-value) occurs while pinging a crafted PNG whose auxiliary chunk stream includes an unrecognized chunk that the reader's generic unknown-chunk callback inspects for an embedded Exif-style marker. The callback allocates a fresh destination buffer sized to hold the chunk's payload (plus the marker prefix it may need to add), and then decides whether to prepend the marker by reading the very first byte of that destination buffer and checking whether it already happens to equal one of the marker's characters. But the destination buffer was just allocated moments earlier and has not yet been written to at all — so this "does it already start with the marker" check is really testing indeterminate heap memory, not anything derived from the actual chunk data the file provided. Depending on how MemorySanitizer's tracking behaves for that never-written byte, this branch on garbage data is exactly the read the sanitizer flags.

The fix removes this nonsensical self-check entirely: it now unconditionally writes the marker prefix into the destination buffer first, and separately checks whether the *source* chunk data itself (not the destination buffer) already begins with the marker bytes, skipping over them if so before copying the remainder in. This way the branch condition is always computed from real, attacker-supplied bytes that were actually read from the file, never from the destination buffer's own uninitialized contents.

fix_commit plausibility: highly plausible: the diff sits directly in the unknown-chunk callback on the crash's own call chain, restructuring the exact branch that previously dereferenced the freshly-allocated destination buffer before anything had been written into it — matching a crash whose allocation-origin trace shows that same buffer being created immediately beforehand.
