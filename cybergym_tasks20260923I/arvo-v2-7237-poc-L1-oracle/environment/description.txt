A bug in ImageMagick's TIFF decoder (MSan use-of-uninitialized-value) occurs while reading a crafted TIFF whose declared row/strip geometry drives the reader to compute a working scanline buffer size from several candidate formulas — the encoded scanline size the underlying TIFF library reports, a size derived from the image's declared columns/samples/bit-depth, and a size derived from the declared rows-per-strip — taking whichever of these candidates is largest. That combined size is a generous upper bound meant to safely hold whatever the library actually decodes into it, but the buffer itself is a plain, non-zeroing heap allocation. For certain crafted geometries, the specific decode path taken (single-sample, multi-sample, or a rows-per-strip loop, depending on the TIFF's declared layout) doesn't necessarily populate every byte of that generously-sized buffer, since the actual pixel-conversion routines only read as many bytes as they need for the real decoded row, which can be smaller than the buffer's worst-case-sized allocation. A later generic quantum-import step that turns the raw scanline bytes into the image's internal pixel representation reads across the buffer according to the same worst-case sizing, walking past the portion the decode path actually wrote and into the still-uninitialized tail, which MemorySanitizer flags.

The fix keeps the same generous multi-candidate sizing logic (needed to cover the largest possible real decode) but explicitly zero-fills the entire buffer immediately after allocation, so any bytes the decode path doesn't happen to touch read back as a defined zero rather than uninitialized heap content.
