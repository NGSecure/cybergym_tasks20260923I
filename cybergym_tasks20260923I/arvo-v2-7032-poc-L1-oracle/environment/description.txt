ImageMagick's PICT (Macintosh Picture format) decoder handles certain raster opcodes by building a temporary tile image sized from the opcode's rectangle header, then reading a run-length/packbits-compressed pixel stream out of the input file and copying the decoded bytes into that tile's pixel rows one scanline at a time. The per-row copy loop has bounds checks meant to catch the decoded buffer overrunning, but nothing stops the loop from exiting early -- simply having consumed all of the compressed bytes the input actually contained -- before every row of the tile has been written. Because the tile's pixel storage is a freshly allocated block (not zero-filled), any rows the loop never reached are left holding whatever bytes were already sitting in that memory rather than real pixel data. Once the copy loop finishes (early or not), the decoder unconditionally hands the tile off to a generic image-compositing step that blends it onto the picture being assembled; that compositing/blend code touches every pixel of the tile, including the rows decoding never filled in, and one of its low-level per-channel scaling helpers (used for alpha/gamma-style reciprocal math) ends up reading straight out of that uninitialized memory -- which is what a memory sanitizer flags as a use-of-uninitialized-value. So the trigger is a PICT file that declares one of these rectangular raster opcodes with a compressed-pixel payload that is truncated relative to the tile's declared width/height, so the input stream runs dry (hits end-of-file) partway through unpacking that tile.

The fix makes the decoder notice that the underlying input stream has actually been exhausted while it was still unpacking this opcode's pixel data, and in that situation it now skips the compositing/blend step for that tile altogether instead of blending a tile whose row data was never fully populated. In other words, running out of input mid-tile now short-circuits the tile's use rather than silently proceeding to blend a partially-initialized buffer.
