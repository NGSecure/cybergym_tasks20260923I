A bug in ImageMagick's MVG arc-primitive renderer (MSan SEGV write) occurs while decoding a crafted MVG document that draws an "arc" primitive. Before the tracing routine walks an arc and writes out its interpolated points, the renderer must first estimate how many points that walk will actually produce, so it can size the shared points buffer accordingly. The estimation code, however, treats the "arc" primitive exactly the same as a "circle" primitive for this purpose — reusing the circle case's own geometry interpretation of the primitive's stored coordinate points (which describes a circle's center and radius) even though an arc's stored points describe a different shape (an off-center span between two endpoints, not a circle centered on one point with a radius to another). Because that geometry interpretation is wrong for the arc case, the coordinate-count estimate it produces doesn't correspond to how many points the arc actually gets subdivided into during tracing, so the points buffer ends up sized for the wrong shape entirely — and for a crafted arc/angle-span combination, the real tracing walk writes far more points than that mis-estimated buffer holds, landing on a completely unmapped address rather than a modest overrun.

The fix splits the arc primitive out into its own dedicated case, computing the correct center-and-radii geometry for an arc (rather than borrowing the circle case's interpretation) before estimating the coordinate count from that, so the buffer this estimate drives is now sized according to the shape that's actually being traced.
