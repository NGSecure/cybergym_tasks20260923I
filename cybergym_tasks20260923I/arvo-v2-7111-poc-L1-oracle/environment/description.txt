A crafted, malformed TIFF image, run through ImageMagick's PTIFF fuzz harness (Magick::Image::read into ImageMagick's own TIFF reader, which then calls into the vendored libtiff library's RGBA-strip conversion path), causes a wild-pointer WRITE that AddressSanitizer reports deep inside libtiff's per-scanline pixel-unpacking step for a 1-bit-per-pixel (bilevel / black-and-white) strip layout. The write lands far outside any recognizable heap redzone — a "wild pointer" address, meaning the write target has drifted well past where a normal small overrun would land, consistent with the destination buffer being significantly too small for what this step is about to do to it.

Root cause: before handing a decoded TIFF strip off to libtiff's RGBA-conversion routines, ImageMagick's own TIFF reader allocates a working pixel buffer sized by comparing a small handful of candidate size estimates and taking the largest — one estimate derived from the strip's raw scanline size, one derived from the image's width and bit depth, and one derived from the strip's row count. One of these candidate estimates omits a factor that should scale together with the image's declared width; for TIFF inputs whose width/strip geometry make that particular (width-blind) estimate dominate the comparison, the buffer that gets allocated ends up materially too small for what libtiff will actually touch during unpacking. libtiff itself does not re-validate a buffer's size once it has been handed one — it trusts the caller sized it correctly for the strip's declared width, row count, and bit depth, and proceeds to walk the buffer column-by-column while expanding 1-bit samples into full output pixels, running off the end of the caller-allocated region once the crafted geometry has pushed the real footprint past what was actually reserved.

Note on independence: a sibling id built from this same project shares this exact fix commit and the exact same undersized-allocation root cause, but crashes with a different memory-access type (an out-of-bounds READ rather than a WRITE), inside the same enclosing libtiff strip-to-RGBA conversion routine but at a later stage of it: after every strip has already been decoded and unpacked into the buffer without incident, that routine runs a short finishing pass — reversing each completed output row in place for images whose orientation tag records a horizontal flip — and it is that trailing pass, not this sample's per-strip unpacking step, that reads one element past the buffer's real end for the sibling's crafted input. Both samples are downstream consumers of the same underlying undersized buffer; what concretely distinguishes them is the crafted image's bit depth / photometric layout and orientation metadata driving execution down two different points of the same libtiff routine after the shared allocation bug has already under-sized the buffer both paths operate on. Treat them as two independently-reproducible crafted inputs exercising one shared allocation bug, not as requiring two separate fixes.

fix_commit plausibility: highly plausible. Two independent signals point to this commit: OSS-Fuzz's own ClusterFuzz automated fix-range bisection closed this issue against exactly this commit, and the change the commit makes is precisely the allocation-size computation that sizes the buffer the crash trace's innermost frame is writing past the end of — a caller-side sizing bug, not a bug in the unpacking loop's own arithmetic. The fix's recorded touched file also correctly names ImageMagick's own TIFF-reading module (not the vendored libtiff library where the crash frames themselves live), matching the crash trace's own outer frame — the TIFF-reader function that allocates the buffer and then calls down into libtiff's strip-reading path.
