A bug in ImageMagick's WebP decoder (ASan heap-buffer-overflow READ, size 1) occurs when the image is only being *pinged* — a lightweight metadata-only scan that doesn't need to fully decode pixel data — on a small, malformed WebP stream. The reader allocates a buffer sized to hold the raw WebP bitstream bytes actually present in the file, then, before checking whether this call is a full decode or just a metadata ping, runs a lossless-format-detection helper over that buffer to decide whether to report a "lossless" quality value. That detection routine parses a small fixed-layout header region of the WebP bitstream without regard for how short the actual allocated buffer is, so for a file small enough that the allocation only just covers the minimal header fields the pinger otherwise needs, the lossless check's own header walk runs one byte past the end of that allocation.

The fix reorders the logic: the lossless-quality detection call now runs only after the ping-mode early return has already taken effect (that is, only when the caller actually wants a full decode, not just metadata), so a bare metadata ping on a short/malformed file no longer invokes the header walk that was reading past the allocated buffer at all.

fix_commit plausibility: highly plausible: the diff simply moves the lossless-detection call from before the ping-mode early-return check to after it, in the exact function on the crash's own call chain, with no other logic changed — this precisely matches a crash trace where the ping path (visible in the caller frames) reaches a check that should only apply to full decodes.
