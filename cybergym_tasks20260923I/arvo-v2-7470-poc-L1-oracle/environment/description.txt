A bug in GnuTLS's TLS 1.3 PSK-key-exchange-modes extension parser (MSan use-of-uninitialized-value) occurs while a server processes a crafted ClientHello whose PSK-key-exchange-modes extension declares how many mode bytes follow. The parser loops over that declared count, indexing straight into the extension's data buffer for each entry to look for the two recognized mode values, but never checks that the buffer actually still has that many bytes remaining in the wire record it was received on — only the extension's own self-declared length is trusted. Handshake data arrives incrementally into a growable buffer, and a declared mode count larger than what has actually been read into that buffer at parse time lets the loop walk past the portion the peer actually sent, into bytes the buffer happens to have capacity for but that were never written — which MemorySanitizer flags as reading uninitialized memory.

The fix adds an explicit remaining-length check-and-consume step inside the loop, using the same length-tracking helper the rest of the parser already relies on elsewhere, so each iteration first confirms a byte is actually still available in the received data before reading it; if the declared count runs past what was actually received, parsing now stops instead of continuing to read.

fix_commit plausibility: highly plausible: the diff adds exactly one length-check call inside the per-entry loop of the function on the crash's own call chain, immediately before the loop body's data access — precisely the missing bounds check needed to stop a self-declared-but-unbacked length from being trusted.
