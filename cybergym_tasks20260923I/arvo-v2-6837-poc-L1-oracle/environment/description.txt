In mupdf's (MSan) PDF content-stream interpreter, rendering a content stream whose fill/stroke operator recurses into a nested tiling-pattern fill triggers a use-of-uninitialized-value read in the generic reference-count-increment helper used by mupdf's resource objects; the interpreter keeps its per-content-stream graphics-state records in one dynamically-growing heap array, and the code that begins rendering a pattern is handed a raw pointer to the parent graphics-state entry that its caller computed against that array *before* the recursive pattern-rendering call runs — but entering the pattern first pushes a new graphics-state level, which can grow (realloc) that same array and relocate it, so when the pattern code then dereferences the caller-supplied parent-state pointer to copy the parent's state into the freshly pushed entry, it is reading through a pointer that the just-performed reallocation has already invalidated rather than through the live array. One of the fields copied this way is a pointer to a shared resource object, and it is exactly that copied-from-stale-memory pointer whose reference count the generic increment helper then reads and bumps, so the uninitialized bytes left behind by the reallocation surface as the increment helper reading garbage instead of a valid refcount. Root cause is therefore a stale-pointer-across-a-possible-reallocation bug in the pattern-fill nesting path (the parent graphics-state reference is captured by address instead of being re-derived by index/offset after the intervening push can move the backing array), not any kind of out-of-bounds index or a wrong-sized/shrunk state array — the array is growing, and the bug is that a pointer taken just before the growth is used just after it.
