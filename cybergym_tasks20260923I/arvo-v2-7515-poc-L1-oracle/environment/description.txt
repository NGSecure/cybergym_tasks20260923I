A bug in ImageMagick's MNG reader (MSan use-of-uninitialized-value) occurs while pinging a crafted MNG file containing a chunk whose declared payload is longer than what the file actually provides. The reader allocates a buffer sized to the chunk's declared length and fills it byte-by-byte from the input stream; when the stream runs out early, the fill loop simply stops there, without raising any error, leaving the unfilled remainder of the buffer as raw, never-written heap memory. Processing then continues as if the whole buffer were valid chunk data. One of the fields this particular chunk type carries is later read to translate a PNG-style rendering-intent value into ImageMagick's own internal enumeration — and if that field happens to fall in the unfilled tail of the buffer, that translation step reads straight from uninitialized memory.

The fix replaces the silent early-stop with an explicit failure: when the input runs out before the declared chunk length is reached, the reader now releases the partially-filled buffer and raises a proper "insufficient data" error, aborting the read instead of quietly continuing with a buffer that's missing its declared tail.

fix_commit plausibility: highly plausible: the diff changes exactly the byte-fill loop's early-exit behavior in the MNG chunk-reading routine on the crash's own allocation-origin call chain, from a silent break to an explicit error-and-release — precisely closing the gap between "how much of the buffer was actually filled" and "how much of it later code assumes is valid."
