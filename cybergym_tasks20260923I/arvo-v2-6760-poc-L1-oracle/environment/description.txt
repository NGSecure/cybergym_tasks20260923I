一句话：解析一种早期黑白位图格式时，若输入在游程（RLE）解码尚未填满整幅固定尺寸画布（576×720）之前就提前耗尽/出错，解码函数仍会无条件对整幅图像做一次"按像素通道值反推调色板索引"的收尾同步，从而读取到画布中从未被解码循环写入过的像素缓存内容。

根因：该解码器一开始就把图像固定为 576×720、深度为 1 的调色板图，并据此建立好像素缓存——这块缓存来自堆分配，分配器本身不做清零/初始化。随后解码器按行做游程解压：每凑齐一整行（列数按位打包）编码数据，就把还原出的 0/1 索引值逐个写入该行像素并提交同步，行号递增。但如果输入数据（游程计数/取反字节）在还没推进到最后一行之前就命中 EOF 或读取失败，外层解码循环会直接跳出——此时尚未被凑满一行、进而被写入过的那些行，其像素缓存仍然是分配时的原始堆内容，从未被任何写入路径触碰过。函数末尾却不区分是否解码完整，无条件对整幅图像执行一次调色板索引重建：该收尾例程会逐像素读取像素的颜色通道值去查找/写回对应的调色板索引下标，对那些被截断、从未写入过的行而言，读到的正是这段未初始化的堆内存，从而被 MemorySanitizer 判定为对未初始化值的使用。

fix_commit 可信度：可信，理由具体。commit 对应的正是这条崩溃在 OSS-Fuzz 上的原始 issue（同一个 crash state：调色板索引写入例程 / 图像整体同步例程 / 该格式的读取函数，三帧完全一致，元数据里的 fix 链接就是该 commit 且 ClusterFuzz 用同一个 testcase 验证过已修复)，改动位置也正好卡在“建立好像素缓存之后、开始逐行游程解码之前”：新增的逻辑在 SetImageExtent 成功后立刻显式重置（清零）整幅图像的像素内容，再继续走原有的解码流程。这正好补上了根因里缺的那一步——不管游程解码提前在第几行终止，凡是没被解码循环覆盖到的行，像素缓存此时已经有一个确定值（重置后的值），而不再是分配器返回的原始未初始化堆内容；末尾那次无条件的调色板索引收尾同步因此不会再读到未初始化内存。变量/条件对得上：改动本身除了新增重置调用外没有改变解码循环的任何逻辑，说明这不是"顺手改别的东西"，而是精确堵住了本次崩溃触发的那条路径。

方向自检：是"读"未初始化值（不是写越界）；未初始化的成因是"分配了但部分行从未被写入"（不是"写了错误的值"）；受影响的是被截断/提前终止的解码所遗留的那些行的像素缓存（不是画布之外的越界内存，画布尺寸本身是固定值、不随输入变化）；修复是"提前把缓存清零垫底"，不是"补上校验直接拒绝畸形文件"。
